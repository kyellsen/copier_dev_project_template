# AGENTS.md — copier_dev_project

House rules: [`AGENTS.canon.md`](AGENTS.canon.md) (profiles `00-core`,
`10-python`) — generated by `~/code/_templates/agents_canon`, never edited here.
This file carries only what is true in *this* repository.

`just check` is the gate here: it verifies **both** canon copies — this repo's
own and the one shipped into every project — and then renders the template for
real. There is no git hook yet, so run it yourself before committing.

## What this repo is

The **generic base scaffold** for every code project: Python 3.13 with uv, just,
ruff, mypy, pytest, the documentation canon, and an optional publication layer
(Typst tooling: `freeze.py`, `prepare_assets.py`, `export_symbols.py`,
`export-pdf`).

It is deliberately the *base only*. Since v3.0.0 everything report- or
thesis-specific lives in its own world repository — `gutachten_bausteine` and
`thesis_bausteine` — which is applied as a second copier layer on top. Roughly
690 lines of report content came out in that cut, including a hard-coded private
address and a stale duplicate bibliography.

Two sibling scaffolds, not to be confused: `copier_project` builds the **data**
side under `~/data/`, and `agents_canon` supplies the house rules this template
vendors.

## Keep it generic — the rule the v3.0.0 cut bought

**Nothing that only one kind of project needs goes in here.** No report chapters,
no thesis structure, no domain schema, no personal data. If a change would be
wrong for a plain data-analysis project, it belongs in an overlay.

Shared ground *does* belong here: `scripts/check.py|clean|common|pipeline|setup`,
the test and lint scaffolding, `schemas/columns.py` as the symbol and unit SSOT
both worlds hang off, and `publication/lib/data.typ`.

## The two anchor points for overlays

They are formulated generically on purpose, so the base never has to know which
overlay exists:

1. `import? 'project.just'` in `justfile.jinja` — the `?` keeps it a no-op when
   no overlay is applied. An overlay ships its recipes as `project.just`.
2. `AGENTS.md.jinja` points at `docs/*/AGENTS.md` — an overlay ships its binding
   text rules there, and the canon's nested-AGENTS rule then applies to them.

An overlay also brings its own copier answers file, so both layers update
independently.

## Canon in every generated project

**This template no longer ships `AGENTS.canon.md` or `.agents-canon`.** A
generated project fetches them itself — `just setup` runs `canon-pull`, and so
can you at any time.

That is not tidiness, it is the house rule: nothing writes into another
repository. Shipping the canon meant this template carried a second copy with
*its own* profile list, and every later `copier update` offered that copy to the
project. On 2026-08-18 an update to a report would have silently replaced
`00-core,10-python,40-science` with the template's `00-core,10-python` and
dropped the science profile — a file the project's own gate then reports as
hand-edited, with no hint where the change came from.

The `canon_profiles` answer **only bootstraps the first pull**. Once
`.agents-canon` exists it is authoritative, so a project can add a profile by
editing that file and running `canon-pull`; a stale copier answer can never
narrow it back. The recipe says so at the point of use.

A project between generation and its first pull is a normal state: the gate's
canon stage returns early when `AGENTS.canon.md` is absent.

## Where a gate belongs

`include_precommit` is not a taste question. It decides whether a generated
project commits behind a gate, and the answer differs by what the repository
produces:

| Repository produces | `include_precommit` | Why |
|---|---|---|
| **Code** (a library, a pipeline, an app) | `true` | A broken commit is a broken artefact. The gate is fast and judges exactly what the next person will run. |
| **Text** (a report, a thesis) | `false` | The deliverable is a PDF, and the gate would check Python nobody touched. What protects the document is `just pub-watch` while writing — a compile error surfaces in a second — and `just deliver` / `just submit`, which refuse a dirty tree and compile fresh. A commit there is a save point, not a publication. |

Blocking a save point over a transient state teaches exactly one habit,
`--no-verify`, and that voids the gate everywhere. It has already happened once
in `ba_ks`.

When it is `true`, the hook is **versioned** in `scripts/git-hooks` and wired in
with `core.hooksPath` — not the `pre-commit` framework. The framework stashes
unstaged work before running, so its verdict describes a tree that never existed;
the versioned hook judges the working tree as it is. That is also why the
generated project no longer carries a `pre-commit` dependency at all: the hook
is nine lines of bash.

## Verifying a change

The template has no tests, because the thing that can break is the render. So
`just check-render` *is* the test: it generates a throwaway project and asserts
that the shipped canon pin still matches its file, that the generated `justfile`
parses, and that the generated Python compiles. Each of those has been shown to
fail on a deliberately broken template.

It renders with `--vcs-ref HEAD` on a local path, which copier resolves to the
**dirty working tree** — so the gate judges what you are about to commit, not
what you last committed. The module name it passes is deliberately long and
awkward, because identifier length and underscores are where the Jinja paths
break first.

`just probe` does the same but keeps the directory, for looking at the result.
For a change you want to be sure about, run the generated project's own gate on
top: `cd /tmp/probe-dev-project && just check`.

A template that renders in your head is not a template that renders.

## Commit default

**Execute** — atomic commits are expected once asked for. Pushing needs its own
word. Tag releases annotated (`git tag -a`); consumers pin `_commit` from the
tag, and `git push --follow-tags` skips lightweight ones.
