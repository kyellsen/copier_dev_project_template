## What this repo is

The **generic base scaffold** for every code project: Python 3.13 with uv, just,
ruff, mypy, pytest, the documentation canon, and an optional publication layer
(Typst tooling: `freeze.py`, `prepare_assets.py`, `export_symbols.py`,
`export-pdf`).

It is deliberately the *base only*. Since v3.0.0 everything report- or
thesis-specific lives in its own world repository — `gutachten_bausteine` and
`thesis_bausteine` — which is applied as a second copier layer on top. Roughly
690 lines of report content came out in that cut, including a hard-coded private
address and a stale duplicate bibliography.

Two sibling scaffolds, not to be confused: `copier_project` builds the **data**
side under `~/data/`, and `agents_canon` supplies the house rules this template
vendors.

## Keep it generic — the rule the v3.0.0 cut bought

**Nothing that only one kind of project needs goes in here.** No report chapters,
no thesis structure, no domain schema, no personal data. If a change would be
wrong for a plain data-analysis project, it belongs in an overlay.

Shared ground *does* belong here: `scripts/check.py|clean|common|pipeline|setup`,
the test and lint scaffolding, `schemas/columns.py` as the symbol and unit SSOT
both worlds hang off, and `publication/lib/data.typ`.

## The two anchor points for overlays

They are formulated generically on purpose, so the base never has to know which
overlay exists:

1. `import? 'project.just'` in `justfile.jinja` — the `?` keeps it a no-op when
   no overlay is applied. An overlay ships its recipes as `project.just`.
2. `AGENTS.md.jinja` points at `docs/*/AGENTS.md` — an overlay ships its binding
   text rules there, and the canon's nested-AGENTS rule then applies to them.

An overlay also brings its own copier answers file, so both layers update
independently.

## Canon in every generated project

`template/AGENTS.canon.md` and `template/.agents-canon` are shipped with the
scaffold, and `template/scripts/check.py` has a `Canon Integrity` stage. That is
how a project is self-contained from birth rather than depending on `~/.config`.

Raising the pinned canon version is a deliberate act: `agents_canon/sync.sh
template` and then a commit that says which version. It does not make any
existing project red — a consumer's gate checks its own local pin.

## Verifying a change

The template has no tests. The proof is a real render:

```bash
copier copy --defaults --vcs-ref HEAD . /tmp/probe && cd /tmp/probe && just check
```

Do this for any change to the Jinja files. A template that renders in your head
is not a template that renders.

## Commit default

**Execute** — atomic commits are expected once asked for. Pushing needs its own
word. Tag releases annotated (`git tag -a`); consumers pin `_commit` from the
tag, and `git push --follow-tags` skips lightweight ones.
